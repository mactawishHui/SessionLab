# 分组缓存性能检查（0.6.0 测速样本）

已更新日常 Chrome，并完成本机 A/B 分组、普通页冷缓存、Header 修改及保存业务会话的 UI 验证。15 项原有集成测试和 12 项缓存检查通过。

本地 Chrome for Testing 148.0.7778.96：同页 96 个可缓存脚本，服务端每个资源延迟 3ms，相同 URL 重复使用。每种情况预热一次后交替测量 5 次；账号及 Header 均为虚构数据。

| 指标 | 0.5.2 | 0.6.0 |
|---|---:|---:|
| 受管分组重复导航耗时中位数 | 174.8 ms | 89.1 ms |
| 重复访问的静态资源服务器请求数 | 96 | 0 |
| 普通页重复导航耗时中位数 | 44.0 ms | 60.5 ms |
| 初次新建组并加载（各 1 次，含初始化） | 246.0 ms | 420.6 ms |

受管重复加载本次降低约 49.0%。这不是业务网站的提速承诺，普通页差异也表明进程和系统负载存在波动。初次加载反而有额外开销：本次优化针对重复打开与同组资源复用，冷加载仍需进一步优化。

服务器计数是缓存命中的依据。Fetch.fulfillRequest 的合成响应在 performance.transferSize 中仍可能显示有传输量，不能将其直接解释为服务器请求。

缓存范围只包括明确 max-age 的脚本、样式、图片、字体；文档及 API 始终联网。缓存按分组、Cookie、Authorization、Header、站点和 Vary 匹配；Cookie / Header / 修改请求会使旧缓存失效。缓存只驻内存，重启或重载扩展后重新预热。

实机发现仅关闭原生缓存和改写响应头仍可能向共享缓存写入内容。最终实现将受管 GET/HEAD 改为扩展自身的 no-store 获取，再以字节响应交回原 Chrome 页面；没有画面转发、远端代理或新增权限。测试同时覆盖普通页已有缓存和从未访问过的资源，以及 API 响应。业务站兼容性不能由本地测试完全证明，具体边界见 [README](../README.md)。

原始样本见 [performance.json](performance.json)，实机记录见 [local-chrome-result.json](local-chrome-result.json)。
